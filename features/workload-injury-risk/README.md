# 負荷・怪我リスク特徴量 PoC

選手トラッキングの実コート座標（cm）から、移動距離・高強度走行距離・ピーク速度といった「怪我リスク予測」「個人特性を考慮したパーソナライズモデル」の土台となる特徴量を設計するフィージビリティスタディ。**怪我発生の正解ラベルが無いため、予測モデルそのものは作れない。** あくまで「この特徴量は実データから作れるか」の検証。

## 結果（0〜70秒、ホモグラフィー較正済み区間）

| 指標 | 値 |
|---|---|
| 分析対象トラック | 71 |
| 移動距離（中央値） | 9.7m（最大55.1m） |
| 高強度走行距離（中央値） | 3.5m（5.5m/s以上） |
| ピーク速度（中央値） | 7.45m/s（95パーセンタイル基準） |

詳細: `outputs/workload_profiles_0_70s.json`

## 手法

1. **速度帯の定義** — walk(<2m/s) / jog(2-4) / run(4-5.5) / high-speed(5.5+)というスポーツ科学で一般的な区分
2. **外れ値除去** — 12m/s超の区間はトラッキングノイズとして除外
3. **二段階の平滑化** — 位置を5フレーム移動平均→速度算出→さらに速度を約0.5秒窓で平滑化してから加速度（急減速）を算出
4. **ピーク速度は95パーセンタイル** — 最大値はトラッキングジッタに弱いため

## 実行

```bash
python analyze_workload.py
```

## 工夫点・つまずいた点（正直な記録）

- **座標系の誤認で秒速数百万mという異常値が出た。** 選手トラッキングの座標を生ピクセルだと思い込み、別途ホモグラフィー変換をかけたところ明らかにおかしい値になった。調査の結果、`outputs/shot_player/tracking_300s.json`の座標は`pipeline/shot_player_analysis.py`内部で**既に実コート座標(cm)に変換済み**だったと判明。二重変換が原因だった（`ball_positions_sam3_300s.json`はピクセル空間なので混同しないこと）
- **急減速カウントは平滑化しても信頼できなかった。** 二階微分はノイズを増幅するため、速度系列をさらに平滑化しても非現実的に高い回数のまま。この指標は不採用と判断した（`hard_decel_count_unreliable`として出力には残している）

## 正直な限界

- 怪我の発生ラベルが無く、単一試合5分間のみのため予測モデルの学習・検証はできていない
- トラックは選手個人ではなくトラッキングのフラグメント。永続IDには[jersey-ocr](../jersey-ocr/)・McByte++によるID統合が必要
- 急減速カウントはノイズ支配で信頼できない
- 実運用の怪我リスクモデル（急性:慢性負荷比等）には複数試合・複数週の縦断データが必要
